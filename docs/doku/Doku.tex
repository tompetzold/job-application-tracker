\section{Einführung und Ziele}

\subsection{Aufgabenstellung}

Der Bewerbungstracker ist eine webbasierte Anwendung zur Verwaltung und Nachverfolgung persönlicher Bewerbungsprozesse.
Nutzer können Bewerbungen erfassen, bearbeiten und nach ihrem aktuellen Status organisieren.
Der Bewerbungsprozess wird vom Entwurf bis zu einem abschließenden Zustand abgebildet.

Die wesentlichen Funktionen sind:

\begin{itemize}
  \item Anlegen, Bearbeiten und Löschen von Bewerbungen
  \item Darstellung der Bewerbungen auf einem Kanban-Board
  \item Ändern des Status per Drag-and-drop oder Auswahlmenü
  \item Prüfung zulässiger Statusübergänge
  \item Anzeige einer Änderungshistorie
  \item Zurücksetzen der letzten Statusänderung
  \item Suche über die Bewerbungsdaten
  \item Anzeige statistischer Kennzahlen
\end{itemize}

Das Projekt dient der praktischen Umsetzung einer Layered Architecture.
Der architektonische Schwerpunkt liegt auf der Trennung von Präsentation, Geschäftslogik und Persistenz.

\section{Lösungsstrategie}
\label{sec:solution-strategy}

\subsection{Layered Architecture}

Die Layered Architecture strukturiert ein Softwaresystem in horizontale Schichten mit klar abgegrenzten Verantwortlichkeiten. Eine Schicht stellt der darüberliegenden Schicht Dienste zur Verfügung und delegiert Aufgaben an die darunterliegende Schicht. Bei einer geschlossenen Schichtenarchitektur werden Schichten nicht übersprungen. Dadurch bleiben Abhängigkeiten gerichtet und die Zuständigkeiten nachvollziehbar \cite{richards2020}.

Für das Backend wurden drei Anwendungsschichten festgelegt:

\begin{itemize}
  \item \textbf{Präsentationsschicht:} Entgegennahme von HTTP-Anfragen, Abbildung von Request- und Response-Daten sowie Zuordnung fachlicher Fehler zu HTTP-Statuscodes.
  \item \textbf{Geschäftslogikschicht:} Validierung von Eingaben, Durchsetzung der Statusregeln, Erzeugung von Historieneinträgen und Koordination fachlicher Abläufe.
  \item \textbf{Persistenzschicht:} Ausführung der SQL-Anweisungen und Abbildung zwischen relationalen Daten und den fachlichen Objekten.
\end{itemize}

\subsection{Umsetzung im Bewerbungstracker}

Das Backend ist als modular gegliederter Monolith umgesetzt. Alle Backend-Schichten werden gemeinsam als eine Spring-Boot-Anwendung gebaut und bereitgestellt. Die Abhängigkeiten verlaufen von der Präsentationsschicht über die Geschäftslogik zur Persistenzschicht. Der Controller greift nicht direkt auf das Repository oder die Datenbank zu.

Das entspricht einer klassischen Layered Architecture, nicht einer hexagonalen Architektur mit Ports und Adaptern. Das React-Frontend ist ein separater Client und gehört nicht zu den internen Backend-Schichten.

\subsection{Datenhaltung}

Die Tabelle \texttt{applications} speichert die Stammdaten und den aktuellen Status einer Bewerbung. Die Tabelle \texttt{application\_history} speichert die zugehörigen Historieneinträge. Zwischen einer Bewerbung und ihren Historieneinträgen besteht eine 1:n-Beziehung. Das Backend lädt die Historie anhand der Bewerbungs-ID und sortiert sie absteigend nach der Sequenznummer.

\subsection{Laden der Bewerbungen}

Beim Start prüft das Frontend zunächst den Endpunkt \texttt{/api/health}. Anschließend ruft es alle Bewerbungen über \texttt{GET /api/applications} ab. Der Controller delegiert an den Service, dieser an das Repository. Das Repository lädt zunächst die Bewerbungen und danach die jeweilige Historie. Die Domänenobjekte werden in Response-Objekte transformiert und als JSON an das Frontend zurückgegeben. Bei einem Fehler leert das Frontend den lokalen Datenbestand und zeigt das Backend als nicht erreichbar an.

\subsection{Persistenz und Änderungshistorie}

Der aktuelle Zustand einer Bewerbung und die historischen Änderungen werden getrennt gespeichert. Dadurch kann der aktuelle Status direkt gelesen werden, während frühere Übergänge für die Historie und statistische Auswertungen erhalten bleiben. Ein Historieneintrag enthält Typ, vorherigen Status, neuen Status, Beschreibung, Erstellungszeitpunkt und einen optionalen Rücksetzzeitpunkt.

Die Persistenzschicht verwendet parametrisierte SQL-Anweisungen über \texttt{JdbcTemplate}. Dadurch werden Nutzereingaben nicht direkt in SQL-Zeichenketten eingesetzt. Bewerbung und Historieneintrag werden derzeit in getrennten Datenbankoperationen geschrieben; die daraus entstehende Konsistenzgefahr wird in Kapitel~\ref{sec:risks} bewertet.

\subsection{Konfiguration und Kommunikation}

Die Backend-Adresse des Frontends ist über \texttt{VITE\_API\_BASE\_URL} konfigurierbar und fällt lokal auf \texttt{http://localhost:8080} zurück. Die Datenbankverbindung wird im Backend durch Spring-Umgebungsvariablen gesetzt. Innerhalb des Docker-Netzwerks wird PostgreSQL über \texttt{postgres:5432} erreicht. CORS ist im Controller für die lokalen Frontend-Adressen \texttt{localhost:5173} und \texttt{localhost:5174} freigegeben.

Die Kommunikation zwischen Frontend und Backend erfolgt synchron. Das Frontend wartet nach schreibenden Operationen auf die aktualisierte Repräsentation der Bewerbung und ersetzt damit seinen lokalen Zustand.
